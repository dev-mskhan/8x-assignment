**Phase 3 PLAN.md — Key decisions**

**12 chunks (A–L), ~17 files to create/modify:**

**Auth flow:**
- JWT access token (15 min, HttpOnly cookie) + refresh token rotation (7 days, path-scoped cookie)
- Refresh mismatch detection — stolen token triggers immediate session revocation
- `bcrypt 12` for passwords (existing utility), `sha256` for reset tokens (high entropy, one-way)
- `forgotPassword` returns identical 200 for found/not-found email — no user enumeration

**Google OAuth PKCE:**
- Server generates `code_verifier` + `state` → stored in Redis with 300s TTL (key: `auth:oauth:state:{state}`)
- State is single-use — deleted from Redis on first read
- Google redirects to `/callback` → server exchanges code → issues our JWT → **redirects to `{FRONTEND_URL}/auth/callback#access_token={token}`** (URL fragment, not query param — never logged by servers)
- Frontend reads fragment client-side → calls `POST /auth/google/verify` → server sets HttpOnly cookies

**Redis usage:**
- Only for PKCE state (ephemeral, 5 min) — no session/user caching (PostgreSQL is truth)
- Redis failure → graceful 500, not silent corruption

**Rate limiting:**
- Tighter per-route limits using `AUTH_RATE_LIMIT_MAX/WINDOW_MS` from env (already in `server.ts`)

**Workers:**
- `AUTH_JOBS.SEND_RESET_EMAIL` via PgBoss — non-blocking HTTP response, Phase 3 logs the link (real email in Phase 10)

**Phase gate:** 30+ integration test cases covering auth lifecycle, RBAC, ownership isolation, rate limits, and security invariants.
