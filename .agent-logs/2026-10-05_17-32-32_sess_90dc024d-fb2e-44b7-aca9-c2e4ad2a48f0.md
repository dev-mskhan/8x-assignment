Here's the complete picture:

---

**Roles**

Three roles defined as a PostgreSQL enum (`userRoleEnum`) and mirrored in the shared `UserRole` type:

```
CUSTOMER   — default for all registrations
SELLER     — marketplace sellers (Phase 5)
ADMIN      — platform administrators (Phase 9)
```

There's no way to register as SELLER or ADMIN through the API — the `createUser` call hardcodes the default, and the registration schema doesn't accept a `role` field. Role elevation has to be done directly in the DB for now (no admin endpoint yet).

---

**How RBAC is implemented**

Two Fastify pre-handler hooks live in `apps/server/src/core/auth/hooks.ts`:

**`requireAuth`** — authentication only
- Reads the signed `access_token` cookie (or `Authorization: Bearer` header in non-prod)
- Calls `verifyAccessToken()` — pure JWT signature + expiry check, no DB lookup
- Sets `request.user = { userId, role, sessionId }` on success
- Throws `UnauthorizedError` (→ 401) if missing or invalid

**`requireRole(...roles)`** — authentication + authorization
- Runs the same token extraction and verification inline (not by calling `requireAuth` — avoids async hook-from-hook issues)
- Then checks `request.user.role` against the allowed set
- Throws `ForbiddenError` (→ 403) if the role isn't in the list

Usage pattern on a route:
```ts
app.post("/seller/products", { preHandler: [requireRole("SELLER")] }, handler)
app.delete("/admin/users/:id", { preHandler: [requireRole("ADMIN")] }, handler)
app.get("/me", { preHandler: [requireAuth] }, handler)
```

---

**What's wired up vs what isn't**

| Hook | Exists | Used today |
|---|---|---|
| `requireAuth` | ✅ | Auth routes, users routes |
| `requireRole("SELLER")` | ✅ | Not yet — no seller routes |
| `requireRole("ADMIN")` | ✅ | Not yet — no admin routes |
| Status check (SUSPENDED/BANNED) | Partial | Only checked at login, not on every request |

---

**One gap worth noting before the next phase**

`requireAuth` is purely stateless — it doesn't hit the DB to check if a session has been revoked. That's intentional for performance (access tokens are short-lived), but it means a revoked session's access token keeps working until it expires. If the next phase introduces sensitive seller or admin actions, you may want `requireRole` to do a DB session lookup for those specific routes, or keep access token TTL short (15 min is the current default).
